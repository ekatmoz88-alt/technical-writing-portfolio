# SOIS — концепция и архитектура служб бортовых интерфейсов

[English summary](README.md) | Русская версия

## Статус и границы материала

Это аналитический архитектурный материал по концепции **Spacecraft Onboard Interface Services (SOIS)** — стандартизованному набору служб для взаимодействия бортовых приложений с устройствами и коммуникационной инфраструктурой космического аппарата.

Материал систематизирует архитектурные уровни, службы, типы интерфейсов и классы качества обслуживания (QoS), а также фиксирует вопросы, требующие сверки с первичными документами CCSDS. Это концептуальный разбор стандартизованной архитектуры, а не описание реализованной бортовой системы и не утверждение об участии автора в разработке космического аппарата.

## 1. Архитектурная задача SOIS

На борту космического аппарата могут применяться различные интерфейсы взаимодействия между вычислительными узлами, датчиками и исполнительными устройствами. Выбор интерфейса определяется характером взаимодействия и требуемыми характеристиками обмена.

SOIS предлагает отделить прикладные приложения от конкретной топологии и электрических/канальных особенностей интерфейсов. Приложения взаимодействуют с унифицированным набором служб, а нижележащие уровни адаптируют эти обращения к доступным каналам и подсетям.

Основная цель — повторное использование приложений и снижение зависимости прикладного ПО от аппаратной конфигурации и коммуникационной архитектуры конкретной миссии.

## 2. Типы бортовых интерфейсов

В рассматриваемой концепции выделяются четыре распространённых типа:

- **Multidrop buses** — общая шина с центральным узлом и несколькими подчинёнными устройствами; обмен часто асимметричен.
- **Point-to-point serial interfaces** — последовательное соединение для управляющей информации и, в некоторых случаях, передачи больших объёмов данных; часто применяется модель master/slave.
- **LANs** — сеть взаимодействия вычислительных узлов сопоставимой мощности, обычно с peer-to-peer обменом.
- **Point-to-point sensor and actuator interfaces** — прямые интерфейсы подключения датчиков и исполнительных устройств.

Эти аппаратные и канальные интерфейсы не должны напрямую определять структуру прикладных приложений: эту изоляцию обеспечивают службы SOIS.

## 3. Уровни архитектуры

### 3.1 User Applications

Прикладные приложения, функциональность которых определяется задачами миссии. Они используют стандартизованные службы SOIS вместо прямой зависимости от конкретной топологии бортовой сети.

### 3.2 Application Support Layer

Предоставляет общие службы, которые могут использоваться приложениями на разных вычислительных узлах. Уровень изолирует приложения от расположения устройств и деталей коммуникационной архитектуры.

Основные службы:

| Служба | Назначение |
|---|---|
| **CDAS — Command and Data Acquisition Services** | Выполнение команд и получение данных от датчиков и простых устройств независимо от их расположения |
| **TAS — Time Access Service** | Единый прикладной доступ к локальному бортовому времени |
| **MTS — Message Transfer Service** | Асинхронный обмен дискретными сообщениями между приложениями, включая multicast и broadcast |
| **FS — File Services** | Доступ к файловому хранилищу и передача файлов в пределах бортовой системы |
| **DES — Device Enumeration Service** | Концепция обнаружения/перечисления устройств для поддержки plug-and-play; состав службы в анализируемом материале обозначен как не полностью определённый |

### 3.3 Transfer Layer

Реализует транспортные и сетевые функции на основе протоколов, разработанных специально для космической связи или адаптированных CCSDS. В качестве примеров в исходном материале рассматриваются IP, SCPS и Space Packet Protocol.

Этот уровень может отсутствовать в конфигурациях, где необходимые функции обеспечиваются непосредственно нижележащими средствами.

### 3.4 Subnetwork Layer

Обеспечивает доступ к канальному уровню и унифицированный набор служб поверх конкретной подсети. В анализируемой схеме физический уровень также показан в составе нижней подсетевой части; такое представление следует сверять с конкретной редакцией нормативной модели и используемыми схемами.

Ключевые службы:

| Служба | Назначение |
|---|---|
| **Packet Service** | Передача пакетов по одной шине/подсети, мультиплексирование протоколов и поддержка QoS |
| **Get Parameter** | Чтение значения параметра локально доступного устройства |
| **Set Parameter** | Запись значения параметра локально доступного устройства |
| **Read Location** | Чтение слова или блока данных из памяти/регистра устройства |
| **Write Location** | Запись слова или блока данных в память/регистр устройства |
| **Time Distribution** | Распространение времени от центрального источника к узлам-потребителям |
| **Device Discovery** | Обнаружение устройств, появившихся вследствие изменения аппаратной конфигурации |

Get/Set Parameter и Read/Write Location в описанном варианте являются локальными асимметричными службами: они обслуживают устройства, доступные узлу, на котором расположен пользователь службы. Для обращения к удалённым устройствам требуется служба более высокого уровня, например CDAS.

## 4. Подсеть SOIS и адаптация к канальному уровню

Подсеть SOIS рассматривается как набор служб, абстрагирующих особенности конкретного канального уровня. В Convergence Sublayer могут реализовываться функции, которых не предоставляет используемая технология канального уровня. Если функция уже поддерживается канальным уровнем, она может быть напрямую сопоставлена соответствующей службе SOIS.

Практический смысл такого разделения — возможность использовать различные физические и канальные технологии через единый набор сервисных интерфейсов, не перенося их особенности в прикладные приложения.

## 5. Качество обслуживания (QoS)

В анализируемом материале QoS описывается сочетанием класса обслуживания, приоритета и идентификатора канала (если используется зарезервированный канал).

Рассматриваются четыре класса:

| Класс | Доставка | Ресурсный канал | Приоритизация |
|---|---|---|---|
| **Best-Effort** | Одна попытка; подтверждение успешной доставки не гарантируется | Нет | Общий приоритет |
| **Assured** | Доставка подтверждается; при невозможности передать данные отправитель уведомляется | Нет | Общий приоритет |
| **Reserved** | Одна попытка; подтверждение успешной доставки не гарантируется | Да | Приоритет в пределах зарезервированных ресурсов |
| **Guaranteed** | Доставка подтверждается; при невозможности передать данные отправитель уведомляется | Да | Приоритет в пределах зарезервированных ресурсов |

Для всех классов в исходном описании отдельно оговариваются ограничения целостности и размера: SDU, полученный из PDU с ошибками, не доставляется; размер отдельного SDU не должен превышать MTU.

### 5.1 Аналитическое замечание: in-sequence, order и out-of-sequence

В исходном описании QoS обнаруживается терминологическая неоднозначность:

- для Best-Effort указывается, что порядок (order) пакетов не обязательно сохраняется;
- одновременно говорится о последовательной передаче (in-sequence) в пределах приоритета;
- далее приводится утверждение, что для Best-Effort и Reserved пакеты, пришедшие out-of-sequence, отбрасываются.

Эти формулировки могут относиться к разным уровням или условиям упорядочивания, однако без точной привязки к нормативным определениям и контексту нельзя считать такое объяснение установленным фактом.

**Вывод анализа:** противоречие следует оставить как вопрос для сверки с первоисточником. Нельзя автоматически трактовать отсутствие гарантии порядка как разрешение доставлять любые пакеты вне последовательности или, наоборот, как безусловное требование их отбрасывать. Также отсутствие слова «полностью» в описании Best-Effort и Reserved само по себе не заменяет нормативного определения гарантий доставки.

## 6. CDAS: доступ к датчикам и исполнительным устройствам

CDAS предоставляет приложениям единый способ командования устройствами и получения от них данных. В рассматриваемой модели выделены три функциональные составляющие.

### 6.1 Device Access Service (DAS)

Базовый, зависящий от конкретного устройства механизм чтения и записи. Он скрывает от пользователя физическое расположение устройства и детали электрического интерфейса, но пользователь должен знать формат команд и данных конкретного устройства.

Базовые операции:
- чтение значения из устройства;
- запись значения в устройство.

### 6.2 Device Virtualisation Service (DVS)

Предоставляет стандартное виртуальное представление физического устройства. Это позволяет приложениям работать с классом устройств через общий интерфейс, не учитывая отдельные аппаратные характеристики.

В исходной концепции DVS обычно использует DAS для выполнения команд и получения данных.

### 6.3 Device Data Pooling Service (DDPS)

Поддерживает общее представление текущих состояний нескольких устройств в виде пула данных. Обновление может выполняться периодическим опросом или поступлением данных от самого устройства (например, по событию/прерыванию).

Пользователь читает данные из общего пула, не инициируя каждый раз отдельный опрос физического устройства. Для такой модели существенны частота обновления, максимальный возраст параметра и точность отражения состояния.

## 7. TAS: доступ к бортовому времени

TAS предоставляет приложению единый интерфейс к локальному источнику времени, синхронизированному с центральным бортовым источником посредством механизмов нижнего уровня.

Важное архитектурное отличие: TAS не обязана напрямую обращаться к службам Subnetwork Layer. Распространение времени между узлами обеспечивается Time Distribution Service, тогда как TAS предоставляет прикладной интерфейс к локальному времени.

В исходном материале выделены три сценария:
- **Wall clock** — чтение текущего времени по запросу;
- **Alarm clock** — уведомление в заданное время;
- **Metronome** — периодические уведомления с заданным интервалом и временем начала.

## 8. Типовые варианты взаимодействия

Материал рассматривает три архитектурных сценария:

1. **Симметричный обмен между интеллектуальными узлами.** Оба узла располагают ресурсами для реализации полного стека SOIS; примером является обмен сообщениями через MTS.
2. **Устройство с частичной реализацией служб.** Контролируемое устройство может реализовывать часть служб Subnetwork Layer, например пакетную службу, если его ресурсы и интерфейсы это позволяют.
3. **Простое устройство без полного стека SOIS.** Для сенсоров и исполнительных механизмов с интерфейсом чтения/записи регистров контролирующий узел реализует необходимые функции SOIS и управляет обменом с устройством.

## 9. Архитектурные выводы

- SOIS разделяет прикладные функции и детали аппаратно-сетевого взаимодействия.
- Application Support Layer предоставляет повторно используемые службы более высокого уровня: доступ к устройствам, времени, сообщениям и файлам.
- Subnetwork Layer унифицирует доступ к функциям конкретной подсети и канального уровня.
- Convergence Sublayer позволяет компенсировать отсутствие требуемых функций в конкретной технологии канального уровня.
- QoS должен рассматриваться как совокупность гарантий доставки, ресурсных ограничений и правил приоритизации, а не как одно числовое значение.
- Выбор обязательных и опциональных служб зависит от профиля реализации; полный набор служб не следует автоматически считать обязательным для каждой конкретной системы.

## 10. Термины и сокращения

| Термин | Значение |
|---|---|
| **PDU — Protocol Data Unit** | Единица данных протокола, содержащая управляющую информацию и, возможно, пользовательские данные |
| **SDU — Service Data Unit** | Единица данных, передаваемая через интерфейс службы |
| **MTU — Maximum Transmission Unit** | Максимальный размер данных, предоставляемых пользователем службе Packet Service |
| **QoS — Quality of Service** | Характеристики качества коммуникационной службы: надёжность, пропускная способность, задержка и другие параметры |
| **SAP — Service Access Point** | Точка доступа к службе |
| **SOIS** | Spacecraft Onboard Interface Services |
| **CCSDS** | Consultative Committee for Space Data Systems |
| **CDAS** | Command and Data Acquisition Services |
| **DAS** | Device Access Service |
| **DVS** | Device Virtualisation Service |
| **DDPS** | Device Data Pooling Service |
| **DES** | Device Enumeration Service |
| **FS** | File Services |
| **MTS** | Message Transfer Service |
| **TAS** | Time Access Service |
| **SCPS** | Space Communications Protocol Specifications |
| **RMAP** | Remote Memory Access Protocol |
| **RTOS** | Real-Time Operating System |
